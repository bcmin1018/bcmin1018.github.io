백그라운드 작업 큐를 만들면 처음엔 보통 큐 하나에 워커를 붙인다. 요청이 적을 땐 문제가 없다. 그런데 한 사용자가 수백 건짜리 작업을 넣은 직후 다른 사용자가 작업을 넣으면, 두 번째 사용자는 **앞 작업이 전부 끝날 때까지 진행률 0%인 화면만 보게 된다.** 시스템 전체는 쉬지 않고 일하는데, 특정 사람만 계속 밀린다.

최근 이 문제를 겪고 **공정 큐잉(Fair Queuing)**을 적용하게 되어, 그 과정을 정리해보았다.

## 배경 — 먼저 들어온 요청이 큐를 독점했다

LLM으로 메일 스팸 여부를 판정하는 작업을 Redis Streams 기반 메시지 큐 하나로 처리하고 있었다. 메일 500건을 A, B, C 세 요청으로 나눠 넣었더니, 워커가 A를 모두 끝낸 뒤에야 B를 시작했다. B를 요청한 사람은 한참 동안 아무 진행도 볼 수 없었다.

이렇게 공유 자원을 쓰는 한 사용자(테넌트)가 다른 사용자의 경험을 망가뜨리는 현상을 **noisy neighbor**라고 부른다. 멀티테넌트 시스템이라면 언젠가 반드시 만나는 문제다.

## 쉬워 보이는 해결책이 통하지 않은 이유

### 워커를 늘린다 → 외부 한도에 먼저 막힌다

LLM API에는 분당 토큰 한도가 있다. 워커를 늘려도 전체 처리량의 상한은 API 한도가 정하므로, 늘린 워커는 한도에 걸려 대기할 뿐이다. 그리고 처리량이 늘더라도 **"A 다음에 B" 순서 자체는 그대로**다. B의 대기 시간이 줄어들 뿐, B가 A 뒤에 서 있다는 사실은 바뀌지 않는다.

### 사용자별 동시 처리 개수를 제한한다 → 줄이 하나면 건너뛸 수 없다

"A는 한 번에 최대 N건까지만 처리"라는 상한을 두는 방법도 떠올릴 수 있다. 그런데 줄이 하나라면 큐의 맨 앞은 여전히 A의 메시지로 가득하다. A가 상한에 걸리면 워커는 멈춰 설 수밖에 없다. 앞의 메시지를 건너뛰고 뒤에 있는 B를 꺼낼 방법이 없기 때문이다(**head-of-line blocking**).

A의 메시지를 일단 읽어서 옆에 쌓아 두는 우회책도 위험하다. 대부분의 브로커는 읽어 갔지만 ack하지 않은 메시지를 일정 시간 뒤 "처리하던 워커가 죽었다"고 보고 다른 워커에게 다시 넘긴다. 쌓아 둔 메시지가 중복 실행되는 것이다. (이 재배달 메커니즘은 [메시지 큐 워커 설계](/algorithms/system-design/message-queue-worker-design/) 글에서 자세히 다뤘다.)

결론은 하나였다. **공정성은 큐가 둘 이상일 때만 만들 수 있다.** 줄 자체를 나눠야 한다.

## 해결 — 줄을 8개로 나누고 돌아가며 꺼낸다

구조는 단순하다.

1. **나눠 담기** — 메시지를 넣을 때 사용자 ID를 기준으로 8개 레인 중 하나를 정해 그 레인에 넣는다. 같은 사용자의 메시지는 항상 같은 레인에 들어가므로 사용자 안에서의 순서(FIFO)는 유지된다.
2. **돌아가며 꺼내기** — 워커는 레인을 한 바퀴 돌며 각 레인에서 조금씩 꺼낸다.

가중치 없이 모든 레인을 똑같이 대하는, 가장 기초적인 **라운드로빈(Round Robin)**이다. 이렇게 흐름(여기서는 사용자)마다 별도 큐를 두고 돌아가며 처리하는 방식을 **공정 큐잉**이라 한다. 원래는 네트워크 라우터가 여러 연결의 패킷을 공평하게 내보내기 위해 나온 개념인데, 작업 큐에도 그대로 적용된다.

Redis Streams는 여러 스트림을 명령 한 번으로 읽는 기능(`XREADGROUP ... STREAMS lane0 lane1 ...`)을 지원해서 구현도 간단했다. 다른 브로커라면 Kafka의 파티션이나 RabbitMQ·SQS의 큐 여러 개가 레인 역할을 한다.

## 놓치기 쉬운 부분 — "몇 건씩" 꺼낼 것인가

라운드로빈은 **누구 것을** 꺼낼지만 정한다. **얼마나** 꺼낼지는 따로 계산해야 하는데, 여기서 실수하기 쉽다.

Redis Streams에서 여러 스트림을 한 번에 읽을 때 `COUNT`(최대 몇 건 달라)는 **전체 합계가 아니라 스트림마다** 적용된다. 워커에 빈자리가 10개라고 `COUNT 10`으로 8개 레인을 읽으면 최대 **80건**이 돌아온다. 빈자리보다 훨씬 많은 메시지를 가져가 버리고, 처리하지 못한 메시지는 앞에서 말한 재배달 문제를 일으킨다.

그래서 요청 개수를 이렇게 정했다.

| 워커의 빈자리 | 요청 방식 | 이번에 가져오는 양 |
|---|---|---|
| 8 이상 (예: 10) | 모든 레인에서 `빈자리 ÷ 8`(버림)건씩 | 레인당 1건 × 8 = 8건. 남은 2자리는 다음에 채운다 |
| 8 미만 (예: 3) | 빈자리 수만큼의 레인만 골라 1건씩 | 3개 레인에서 1건씩 = 3건. **다음엔 이어지는 레인부터** 시작 |
| (잘못된 예) 10 | 모든 레인에 10건씩 | 최대 80건 — 70건이 넘친다 |

빈자리가 8보다 작을 때 매번 레인 0부터 고르면 뒤쪽 레인은 영영 차례가 오지 않는다. 마지막으로 고른 레인 위치를 기억해 두고 다음에 이어서 고르는 것이 라운드로빈의 핵심이다.

## 결과 — 모두가 동시에 진행되기 시작했다

A가 끝나야 B가 시작되던 흐름이 이제는 A, B, C가 섞여서 함께 진행된다. 처리량의 상한은 여전히 API 한도가 정하므로 **전체 완료 시각은 비슷하다.** 대신 B를 요청한 사람이 "내 작업이 진행 중"임을 확인하는 시점이 크게 앞당겨졌다.

애초의 문제가 "느리다"가 아니라 "특정 사람만 계속 밀린다"였으니, 이것이 핵심 개선이었다. 공정 큐잉은 시스템을 빠르게 만드는 기법이 아니라 **기다림을 고르게 나누는** 기법이다.

## 라운드로빈으로 부족해지면

라운드로빈은 **건수만 공정하다.** 메일 한 건의 처리 시간이 비슷한 지금은 충분하지만, 조건이 바뀌면 다음 알고리즘들을 고려할 수 있다.

| 이럴 때 | 방법 | 한 줄 원리 |
|---|---|---|
| 고객별 우선순위가 필요하다 | Weighted RR / WFQ | 중요한 레인에서 더 많이 꺼낸다 |
| 작업마다 크기가 크게 다르다 | DRR (Deficit Round Robin) | 레인마다 "쓸 수 있는 몫"을 매 바퀴 충전하고, 몫이 작업 크기보다 클 때만 처리한다 |
| 사용자가 수천 명 이상이다 | SFQ (Stochastic Fair Queuing) | 사용자를 해시로 고정된 수의 레인에 나눠 담는다 |
| 무료/유료 등급으로 나눈다 | CBQ (Class-Based Queuing) | 등급별로 먼저 나누고, 등급 안에서 다시 돌린다 |

사실 사용자를 레인 8개에 나눠 담는 지금 구조는 이미 SFQ에 가깝다. 사용자가 8명보다 많아지면 한 레인을 여러 사용자가 나눠 쓰게 되고, 같은 레인 안에서는 다시 먼저 들어온 쪽이 앞선다. 레인 수를 늘리는 것으로 어느 정도 버틸 수 있지만, 작업 크기 편차까지 커진다면 **DRR이 다음 단계**다. DRR은 계산이 가벼우면서도 작업 크기가 들쭉날쭉할 때 공정성을 유지해 주어, 작업 스케줄링에서 널리 쓰인다.

## 정리

1. **공정성은 큐가 둘 이상일 때만 만들 수 있다.** 줄이 하나면 워커 증설이나 동시성 제한으로는 앞 요청을 건너뛸 수 없다.
2. **공정 큐잉은 속도가 아니라 순서의 문제를 푼다.** 전체 완료 시각은 같아도, 모든 사용자의 대기 시간이 고르게 나뉜다.
3. **라운드로빈은 "누구 것"과 "얼마나"를 따로 정해야 한다.** 여러 레인을 한 번에 읽을 때 개수 상한이 레인별로 적용되는지 확인하지 않으면 워커가 감당 못 할 만큼 가져온다.
4. **가장 단순한 라운드로빈에서 시작하고, 필요가 생기면 올라간다.** 우선순위가 필요하면 WFQ, 작업 크기가 제각각이면 DRR, 사용자가 많으면 SFQ다.
